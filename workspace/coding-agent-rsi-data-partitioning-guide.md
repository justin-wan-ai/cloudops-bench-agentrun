# Coding Agent 递归自我改进（RSI）数据划分策略指南

在基于爬山法（Hillclimbing）或递归自我改进（RSI）迭代 Coding Agent 时（如自优化 Prompt、修改 Agent Harness 运行代码、重构工具链或控制流），传统机器学习的切分方式（如随机 8:1:1）会导致严重的虚假增益。

本指南提炼 2026 年前沿研究（RRSI, PwC, VeRO 等）的实证结论，为 Coding Agent 在不同 RSI 场景下选择合适的数据划分策略提供工程指导。

---

## 一、 RSI 数据划分的底层公理与典型失效模式

在配置数据划分前，必须理解 Agent 迭代中特有的四种失效物理约束：

1. **噪声裁判下的小样本胜者诅咒（Winner's Curse under Noisy Evaluator）**
   * *机理*：在单次迭代中，评估器（LLM-as-a-judge 或偶发通过的单元测试）具有随机噪声。若在微型验证集上频繁爬山比选，Agent 会筛选出“恰好利用了评估噪声”的劣质变异。
   * *防范*：不可过度依赖微型验证集的单次胜出；必须通过海量保留测试集做终局过滤，或在选择机制中加入统计噪声容忍下限。
2. **分布外增益塌缩（OOD Gain Collapse）**
   * *机理*：未做正则化约束的 Agent Harness 进化，极易在当前演化集（Evolve Set）上刷出高分，但在未见过的任务或新代码库上增益完全塌缩，甚至比初始 Baseline 倒退（实证可导致 -1.7 分的净损失）。
   * *防范*：禁止使用单一基准完成整个 RSI 闭环，必须设置分布外保留基准（OOD Held-out Suites）。
3. **样本规模膨胀诱发的代码与 Prompt 臃肿**
   * *机理*：工业实践表明优化样本并非越大越好。单轮优化暴露过多训练案例（如超过 500 例），Agent 的反思机制会倾向于将长尾特例全部写进规则或 Prompt，造成上下文膨胀（实证可使长度暴增 75%）并削弱泛化能力。
   * *防范*：单轮迭代的反思/训练样本量严格控制在 **20~100 样本区间**。
4. **代码库/主题污染（Data Contamination）**
   * *机理*：若在同一个 Repository 或关联度极高的子模块间做随机切分，Agent 会通过代码上下文提取特异化知识或接口特例，伪装成通用推理能力。
   * *防范*：切分必须以 **Repository-Disjoint（代码库完全隔离）** 或 **Topic-Disjoint（任务主题完全隔离）** 为硬性红线。

## 二、 三大典型场景切分策略决策矩阵

根据 Coding Agent 改进的目标客体（Prompt、Python Harness 还是模型本体），匹配对应的数据切分架构：

| 迭代场景 | 改进目标 | 推荐划分架构 | 优化集配置 (Train / Val) | 测试集配置 (Test) |
| :--- | :--- | :--- | :--- | :--- |
| **场景 A：元提示词与反思优化**<br>(Prompt/System Instructions) | 改进规划、Debug、自我纠错等文本策略 | **极端倒挂 + 主题隔离**<br>(Extreme Skew) | **Train 20~50 样本** (~5%)<br>**Val 20~50 样本** (~5%) | **Test 500+ 样本** (~90%)<br>*完全零交叉主题* |
| **场景 B：代码级 Harness 自演化**<br>(Agent Tool/Control Flow/Harness) | 优化调度代码、Bash 工具链、状态机控制流 | **演化集 + 跨域 OOD 基准**<br>(Evolve vs. OOD Suites) | **Evolve Set**：选用 2~3 个内部环境，单轮预算 B≤8 | **OOD Suites**：完全隔离的外部基准（如 SWE-bench, 外部私有仓库） |
| **场景 C：双层嵌套协同演化**<br>(Inner Harness + Outer RL/Weight) | 内层改 Python 工作代码，外层通过 GRPO 训模型 | **双层解耦划分**<br>(Bi-level Separation) | **内层**：任务诊断样本池（几十例验证选拔） | **外层**：大规模策略优化任务流（数百例 RL 更新与跨学科验证） |

## 三、 场景工程实操指南

### 场景 A：Prompt 与元指令反思优化（极端倒挂策略）

*适用场景*：优化 Coding Agent 的 System Prompt、Code-Review Prompt 或反思模板。

```text
[全部数据 (100%)]
  ├── Train Split (~5%, 20~50 样本)   --> 提供报错 Trace，供 Optimizer 提取反思修改
  ├── Val Split   (~5%, 20~50 样本)   --> 爬山候选 Prompt 的中间态筛选（带门控）
  └── Held-out    (~90%, 500+ 样本)   --> 主题/代码库完全隔离的终局真实评估
```

* **执行规范**：
  1. **低样本反思**：Train 仅输入典型报错 Trace（如语法错误、死循环、工具调用格式错误）。
  2. **噪声门控选择**：候选 Prompt 在 Val 上的胜出幅度若低于预设的噪声阈值（如绝对提升 < 2%），直接舍弃本次变异，避免把噪声当收益。
  3. **终局一次性评估**：Held-out 集在迭代过程中完全物理封存，仅用于最终发布验收。

---

### 场景 B：代码级 Harness / Tool 结构自演化（跨域 OOD 隔离）

*适用场景*：Agent 具备写代码能力，自主修改 `agent.py`、`tools/`、上下文管理逻辑或多智能体交互拓扑（如基于 VeRO 或 RRSI 架构）。

```text
               ┌── [Evolve Set (内部演化任务)] ──┐
               │  - Train (提供 Trace 与变异上下文)│
               │  - Critic / Noise Floor Gate    │
[任务基准总库] ─┤  - 预算控制 (Budget B = 8 步左右) │
               └─────────────────────────────────┘
                               │
               ┌── [OOD Held-out Suites (外部基准)] ┐
               │  - 跨域外部环境（完全不参与演化）    │
               │  - 验证泛化性，拦截过度拟合        │
               └─────────────────────────────────┘
```

* **执行规范**：
  1. **放弃传统单一静态验证集**：不要试图在一个通用 Benchmark 上划 8:1:1 做 Harness 演化。
  2. **演化集配比**：在 Evolve Set 内，Agent 探索步数（Budget）需做硬约束（通常设为 6~10 轮迭代）。
  3. **正则化检查器（Regularization Critic）**：在接受代码改动前，检查代码差异（Git Diff），严禁出现硬编码特异化正则、特定测试集用例字面量。
  4. **OOD 拦截测试**：每当在演化集上获得阶段性最佳 Harness 时，挂载到 2~3 个全新分布（例如在 Terminal 演化，拿到全新的 Web 或 SWE 仓库环境测试）。若 OOD 增益为负，强制回滚该版本。

---

### 场景 C：双层嵌套自改进（Harness 变异 + 模型策略更新）

*适用场景*：结合了代码工作手册/环境重构，以及基于执行结果的强化学习（如 GRPO 权重微调）。

* **执行规范**：
  1. **内层（Harness 优化层）**：
     * **目标**：固定模型本体，改进 Agent 的交互脚手架、单元测试执行器与 Debug 工作流。
     * **数据配置**：轻量交互集。利用几十个诊断任务捕获交互瓶颈，由辅助诊断模型提出代码补丁。
  2. **外层（RL 参数训练层）**：
     * **目标**：固定内层产出的优质 Harness，运行策略梯度更新。
     * **数据配置**：大规模多样化任务池。通过多轮采样（Rollout）获得结果反馈，更新底层模型，并在未参与训练的子任务族上验证迁移效果。

## 四、 自动化检查清单（Checklist）

在启动 Coding Agent RSI 循环前，执行以下排查：

- [ ] **是否已隔离代码仓库（Repo-Disjoint）？**
  * 训练集和测试集不得属于同一 GitHub Repository 或具有相同依赖的私有子包。
- [ ] **优化集规模是否落在甜蜜区？**
  * 单轮反思与梯度更新的样本总量是否在 20~100 之间。避免将超 500 个样本堆入反思上下文。
- [ ] **评估环境是否物理隔离（Sealed Execution）？**
  * Agent 在编写、修改自身代码时，测试集的执行环境、断言文件是否已物理卸载或脱机，直到打分阶段才以只读形式挂载。
- [ ] **是否设定了噪声容忍门控？**
  * 爬山算法在判断新版本是否“优于”旧版本时，是否包含了标准差容忍下限，而非只要 Val 准确率出现 0.1% 的数值上升就盲目合并分支。
- [ ] **是否配置了 OOD 熔断机制？**
  * 是否有至少一套分布外（跨技术栈、跨语言或跨任务类型）的独立验证基准，用于探测 RSI 是否在演化集上发生退化。
