# AgentRun 迁移手册（端到端落地版）

> **版本**：v3.0 · 2026-10-21
> **适用对象**：把一个「高频、可验证、输入结构化」的 agentic task，从「自由 agent 每次重新探索」迁移为「AgentRun 式固定流程 + jev 微判定 + 兜底 agent」。
> **读者**：人类负责人（看原理、门禁、验收）+ coding agent（第 9 章是自主执行契约；P0–P9 是施工图）。
> **实证来源**：`README.md` 记录的 ExCyTIn 安全日志问答迁移（test 522：33.5% → 66.9%，train 50：20% → 46%），以及 `DSL_v2_迭代方案.md`、`DSL_v2_环境恢复与基线复现.md`、`DSL_v2_交接文档.md` 中 40+ 轮实验的正负结果。
> **本文目标**：换一个领域（例如 BI 分析），一个 coding agent 只读本文件 + 领域资料，就能从零把 AgentRun 迁移端到端做完，并在遇到岔路时做出和本文一致的选择。

## 0. 十分钟读懂

### 0.1 一句话

> **让高阶 agent 做一次昂贵的探索，把探索沉淀成 DSL 固定流程；固定流程里只保留少量「类型化判定点」交给 LLM/jev，其余全部退化为确定性代码；任何不确定都走有明确 predicate 的 escalate，而不是让模型自由发挥。**

三个关键词：

| 关键词 | 含义 | 反例（本项目踩过） |
|---|---|---|
| **沉淀** | 把「探索动作」变成「参数化查询计划」 | 每次问都 `SHOW TABLES` / `DESCRIBE` / 全表 profiling |
| **收窄** | 用题面锚点把候选从「全库」压到「≤8 个」 | 放宽绑定/放回噪声，候选一多，LLM 反而选错 |
| **兜底** | 不确定就升级，不硬答 | 单候选强行加「语义闸门」，−71pp |

### 0.3 三个口径，永远不要混

| 口径 | 定义 | 用途 | 本项目数值 |
|---|---|---|---|
| **机制侧** | 只跑 DSL + 机械 jev 回退，`--jev-in /dev/null` | 判断「流程/代码改得对不对」 | 最近完整机制口径：v2.27 = 283/522 = 54.2%（v2.30 未单独测机制） |
| **含答案** | DSL + LLM 作答的 jev 答案库 | 判断「端到端上限」 | v2.30 + `jev_ans_v224` = 349/522 = 66.9% |
| **生产** | 含答案 + 在线 LLM jev + 实时兜底 | 判断「真实成本/延迟/稳定性」 | 需另行压测 |

> **铁律**：验收看机制侧，宣传看含答案，上线看生产。三者混用会得出错误结论（本项目 v2.7 曾出现「机制 +4pp、含答案只 +2.3pp」的口径争议）。

### 0.4 本手册怎么用

- **人类**：读第 1、5、8 章；用第 3 章的门禁表做验收；用第 7 章的 BI 例子对齐预期。
- **coding agent**：先读第 9 章执行契约，再按第 3 章 P0→P9 顺序施工；每阶段结束必须产出「产物 + 门禁证据 + ledger 记录」，否则不得进入下一阶段。
- **任何人**：遇到分歧，先查第 5.5 节「负结果登记表」和第 8 章「实证账本」，避免重走已证伪的路。

### 0.5 术语

| 术语 | 含义 |
|---|---|
| **锚点（anchor）** | 从输入题面/工单里确定性抽取的约束：时间、实体 ID、告警标题、主机名、账号、文件名…… |
| **计划（plan）** | 一条参数化查询：`(表, 目标列, WHERE 绑定, 聚合)`；由锚点 + 先验生成，按优先级排序 |
| **候选（candidate）** | 一条计划执行后得到的去重值 + 计数（+ 可选元数据） |
| **jev** | 类型化判定节点：classify / route / sift / pick / verify；输出枚举、下标或校准概率 |
| **rid** | 一次 jev 决策的稳定标识：`[tag:]<task_id>#<plan_index>` 或 `#bare` |
| **机制级改动** | 不依赖 test GT 的规则/表示/计划改动；可泛化 |
| **答案级改动** | 只改 jev 答案库，不改流程；易过拟合，必须审计 |
| **兜底（escalate）** | 触发 predicate 后交给 judge agent 做受限探索 |

### 0.6 最小可行迁移（MVP，10 步）

如果你只有 2–3 天，按这 10 步做一个能跑通的最小闭环，再回头补 P3 的规模化轨迹：

1. 选 100 条可自动判定的样本，切 70 dev / 30 test，立即冻结；
2. 用 frontier agent 跑 30 条，记录答案、工具调用、耗时、成本（P0 基线）；
3. 写出「输入 → 锚点」的正则/词典（P4 Step 1）；
4. 写 2–3 条参数化查询，验证「gold 是否落在候选集」（P4 Step 2）；
5. 定义 1 个 `classify` + 1 个 `pick`，并规定弃权返回 -1（P4 Step 3）；
6. 实现 runner：`--dsl`、`--tasks`、`--jev-req`、`--jev-in`、`--eval-out`（P5）；
7. 跑机制侧基线；跑 pass A 收请求；
8. 人工/LLM 作答 30 条（去敏后），跑 pass B；做泄漏审计（P6）；
9. 做一轮诊断（漏斗分层）→ 一个单变量改动 → test + train 判定（P7）；
10. 写 `state.md` + `06_ledger.md` + 复现命令，确认 `/tmp` 无资产（P9 交接包雏形）。

> MVP 的验收不是分数，而是：**同配置可复现、改参数行为会变、答案可回放、失败可归因**。这四点成立后，再加样本和机制。

# 第一部分　原理

## 1. 为什么是 AgentRun

AgentRun 针对企业级、高频重复的知识型工作（合规审查、反洗钱、安全事件响应、BI 取数、理赔初审……）重新设计，核心理念是：

> **让高阶智能体做一次昂贵的探索，将其沉淀为标准工作流，然后让大模型从绝大多数日常流程中「退场」。**

### 1.1 四条第一性原理

**原理一：知识沉淀与自动化迭代（Let the agent do the job, then fire itself）**

- 初始阶段由 frontier 模型（Opus/GPT 级）完整执行任务并记录 trace 与笔记；
- 分析 trace，把「通用规则」转化为结构化工作流；
- 95% 以上常规案例走程序化流程，仅疑难杂症交回高阶 agent。

**原理二：决策与行动解耦（Separation of Decision and Action）**

- **行动**：确定性代码、SQL/API 调用、专用轻量 agent；
- **决策**：结构化、校准概率的类型化问题（jev），做到「判断有分值、审计有依据」。

**原理三：异构算力的性价比分工**

| 工作性质 | 承担者 | 成本量级 |
|---|---|---|
| 解析、算术、日期、规则匹配、SQL 执行 | `code` / `call` | 微秒–毫秒 |
| 二分类/多分类/候选选择 | `jev`（小模型或 LLM 单次调用） | 毫秒–秒 |
| 检索、浏览器、多页面浏览 | Research Agent | 秒–分钟 |
| 高风险合规终审、开放探索 | Judge Agent | 分钟–小时 |

**原理四：离线回放评估与模型治理（Replay & Governance）**

- 所有输入、中间判定问题、概率、证据行完整保留；
- 策略/代码微调时直接离线 replay，无需重复调用大模型；
- 几分钟完成海量回归，满足合规审计与模型治理。

### 1.2 成本模型：为什么必须把模型赶出主路径

设单题成本为：

```
C_task = N_explore × C_explore + N_reason × C_reason + N_sql × C_sql + C_report
```

自由 agent 的问题是 `N_explore` 和 `N_reason` 都随题面复杂度线性增长，且每次重复。AgentRun 把：

- `N_explore` → 0（表/列/关联键在编译期固定）；
- `N_reason` → 1–2 次受限 jev；
- `N_sql` → 2–4 条参数化查询；
- `C_report` → 仅最终渲染。

本项目的单题改写照（`agentrun_rewrite_incident134_task49.md`）：

| 指标 | 原始 GPT-5.4 轨迹 | AgentRun 改写 |
|---|---|---|
| bash / SQL 调用 | 8 次（其中 3 次纯探索，37.5%） | 3 条参数化 SQL |
| 模型推理回合 | ~10 回合 / 20 条消息 | 2 个 jev + 1 次报告 |
| 探索动作 | `SHOW TABLES` / `DESCRIBE` / 分布 profiling | 全部剪除 |
| 正常路径模型消耗 | 全程 | 仅 jev + report |

> **迁移的第一个验收指标不是准确率，而是「主路径模型调用次数」和「SQL 次数」。** 如果改写后模型调用没有下降，说明探索没有被真正沉淀。

### 1.3 95/5 分流与「不降级」结构

AgentRun 不是「用流程替代 agent」，而是「用流程吃掉 95%，把 5% 更贵地交给 agent」。因此设计上必须保证：

1. **正常路径**：确定性代码 + jev，可离线 replay；
2. **异常路径**：`escalate(predicate)` 有明确触发条件，交回 judge agent；
3. **结构性不降级**：即使 jev 全失效（准确率 0%），流程也不能比基线差。

本项目 522 题统一模板的上界测算（`agentrun_unified_template_522.md`）：

| 情景 | 检测率 | 对比 GPT-5.4 基线 80.8% |
|---|---|---|
| jev 上界 88.6% | 92.6% | +11.8pp |
| jev 实测 49%（无证据佐证） | 89.5% | +8.7pp |
| jev 全失效 0% | 84.6% | +3.8pp |
| 盈亏平衡点 | jev ≥ 0% | 结构性不低于基线 |

不降级的原因：113 题「唯一候选直选」是确定性净增；其余回落 agent 后按基线率折算仍高于基线；结构性损失仅 2 题（0.4pp）。

> **落地含义**：先把「确定性直选」和「escalate 兜底」做对，再优化 jev。顺序反了会得到「准确率抖动但不可解释」的系统。

### 1.4 什么时候「不该」用 AgentRun

以下任务不适合本手册的迁移方式，应在 P0 直接否决：

| 特征 | 原因 | 替代方案 |
|---|---|---|
| 每个输入都需要开放式研究/多跳假设 | 无法沉淀为稳定计划 | 保留 Research Agent + 缓存 |
| 没有可自动判定的验收标准 | 无法爬山、无法回放 | 先建立 judge/人工抽检协议 |
| 输入 schema 每周变 | 计划层持续失效 | 先做 schema 治理/语义层 |
| 样本量 < 100 且低频（< 10 次/周） | 沉淀成本 > 收益 | 直接用 agent + prompt |
| 答案本身是长文创作 | 行动不可枚举 | 只沉淀「取数与校验」，报告仍交给 agent |
| 强合规要求「每次必须重新推理」 | 流程化不被允许 | 用 replay 做辅助审计，不替代决策 |

### 1.5 任务类型 → AgentRun 映射

| 任务类型 | 典型输入 | 确定性部分 | jev 判定点 | 兜底 |
|---|---|---|---|---|
| **实体抽取**（ExCyTIn） | 告警问答 + 日志库 | 锚点抽取、计划、SQL、形状过滤 | classify 类型 / pick 候选 / verify | 受限 SQL 探索 |
| **BI 取数** | 自然语言问题 + 数仓 | 语义层、指标定义、SQL 生成、guardrail | classify 意图 / pick 口径与维度 / verify 粒度 | 只读数仓探索 |
| **合规审查** | 合同/工单 + 规则库 | 条款抽取、规则匹配、diff | route 适用规则 / pick 条款 / verify 风险等级 | Judge 终审 |
| **工单路由** | 工单文本 + 历史 | 关键词/实体抽取、SLA 计算 | classify 类别 / route 队列 | 人工 |
| **对账/异常检测** | 两方流水 | 匹配算法、金额容差、时间窗 | pick 匹配对 / verify 差异原因 | 人工复核 |

> 迁移时先判断「答案能不能被一个结构化查询 + 少量语义判断唯一确定」。能，则 AgentRun；不能，则只沉淀前半段。

# 第二部分　DSL 参考

## 2. AgentRun DSL 的组成

整个程序由「卡片」组合而成：**Prerequisites / Nodes / Shapes**。

### 2.1 Agent 角色

| 角色 | 职责 | 边界 |
|---|---|---|
| `Research` | 搜索、抓取、登录、多页面浏览 | 只读；有步数预算 |
| `Judge` | 复杂分支、疑难裁决、escalate 终点 | 可读全库；必须输出结构化结论 |
| `Report` | 根据结构化记录渲染最终文档 | **不参与二次决策** |
| `Operator` | 拥有外部写权限 | 严格沙箱 + 紧缩授权 + 人工确认 |

### 2.2 机械与确定性步骤

| 节点 | 用途 | 要求 |
|---|---|---|
| `code(logic: "x")` | 解析、算术、日期、规则匹配、SQL 拼装 | 纯函数；无网络；可单测 |
| `call(tool: "x")` | 外部工具调用、状态轮询 | 超时、重试、只读开关 |
| `artifact(logic: "x")` | 交付物校验、落盘、trace 持久化 | 幂等；带 schema 版本 |

### 2.3 Jev 决策节点

| 类型 | 问题形态 | 输出 | 典型用法 |
|---|---|---|---|
| `classify` | 这条输入属于哪一类？ | 枚举 + 概率 | 问的是 file / account / ip / metric？ |
| `route` | 应该走哪条证据族/分支？ | 分支名 + unsure | 告警属性 / 遥测 / 身份 / 邮件？ |
| `sift` | 这批条目里哪些满足条件？ | 子集 | 过滤非外链、非目标时间窗 |
| `pick` | 哪个候选最匹配？ | 下标或 `-1` | 从 ≤8 个候选值中选答案 |
| `verify` | 这个结论是否成立？ | 置信度 0–1 | 单位、粒度、时间窗是否正确 |

**jev 契约（必须写进 DSL 注释和 runner）：**

1. 输入必须是**受限**的：`question + anchors + target + cands[:N]`，不允许把整库/整表塞进去；
2. 输出必须是**可机械消费**的：枚举、下标、概率，不允许自由文本；
3. 未作答必须用**显式弃权**（`-1` / `unsure`），且弃权后交回**确定性回退**；
4. 每个 jev 决策必须落盘 `rid`、输入摘要、答案、置信度，供 replay 与审计。

### 2.4 组合控制形状（Shapes）

| Shape | 语义 | 边界 |
|---|---|---|
| `chain` | 顺序执行 | 无隐式状态；每步显式 in/out |
| `map / reduce` | 并行处理列表项并收敛 | 并发上限；失败隔离 |
| `loop(until, max_waves)` | 有界循环 | **必须有 max**；必须有 until 条件 |
| `escalate(predicate, fallback)` | 异常分支跳转 | predicate 必须可机械判定 |

**loop 的诚实语义**（本项目实现边界，必须照抄到你的 runner 文档）：

- 循环体内节点的**存在性**决定对应步骤是否执行（去掉 `tighten` 就不收紧）；
- 执行顺序仍是固定语义（call → branch → relax/tighten → pick → precheck → verify），**不是逐行解释器**；
- `code` 节点内部实现仍在 runner 代码里，DSL 决定**链路与参数**。

> **反模式**：把 DSL 写成「看起来像代码、实际只有文档作用」。本项目曾出现 runner 完全不读 DSL、版本文件只是文档的情况，导致「改了 DSL 但行为不变」的假实验。**P5 门禁必须验证：改一个 params 值，行为必须变。**

### 2.5 节点图（以 ExCyTIn v2.30 为例）

```
extract_anchors(code)
  → jev(classify, 机械 pre_rules 短路)
  → jev(route, 机械)
  → build_plan(code)   ← 候选(表,列) = priors.tc_priors[bucket] ∪ 角色列名泛化 ∪ tok_tc
  → loop(until solved, max_waves=6) {
       call(sql) → cardinality_branch(zero|unique|few|many)
       zero  → relax_or_pivot（丢最不信息化锚点 / AlertId 直连 pivot）
       many  → tighten（补锚点）+ jev(pick)★
       unique|few → 形状闸门 → 直选或 jev(pick)★
       value_regex_precheck → jev(verify)
     }
  → escalate(no_plan / waves_exhausted / shape_empty / many_abstain)
  → normalize_answer(code)
  → agent(report)
  → artifact(persist_trace)
```

### 2.6 参数面（声明式）

好的 DSL 把「策略」放 params，把「结构」放 chain。本项目 v2.30 的参数面：

```jsonc
{
```

**参数设计四原则：**

1. **一个参数一个机制**，不要把三个改动塞进一个布尔；
2. **默认值与历史基线一致**，实验参数显式写在版本文件里；
3. **参数必须有文档、有消融记录**（见 `dsl_versions/README.md` 的版本↔成绩表）；
4. **禁止环境变量开关**：环境变量不可回放、不可审计、容易「以为改了其实没生效」。本项目已把所有 env 开关删除，改为 DSL params。

### 2.7 六条铁律（不可破）

| # | 铁律 | 违反后果 |
|---|---|---|
| 1 | WHERE 绑定只来自输入锚点 | 用 GT 反查 = 作弊，成绩无效 |
| 2 | 求解路径任何节点不得读 GT | 同上；P6 泄漏审计会抓出来 |
| 3 | 统计先验只做排序，不做硬规则 | 先验置顶会挤掉旧候选（本项目 G1 −1.3pp） |
| 4 | jev 未作答必须回退确定性规则 | 弃权后机械往往更准（本项目 4 次验证） |
| 5 | 任何放宽（绑定/形状/噪声）必须先证明不放宽会漏 | 放宽通常让噪声顶掉正确答案（6 次负结果） |
| 6 | 改候选集必须同时迁移答案库 | 按位置索引的答案会整体错位（v2.28 −27） |

### 2.8 DSL 设计模式

**模式 A：锚点驱动收窄（Anchor → Plan → Candidate）**

```
题面 → 确定性抽锚点 → 锚点映射到 (表,列) → 参数化 WHERE → 候选集
```

- 锚点必须**有信息量排序**（本项目：`cmd < actor < file < account < ip < pid < host < ts < alert`）；
- 零行时按信息量**从低到高丢弃**重试，不要一上来全表扫描；
- 绑定过窄是常见病：先诊断「整列是否含答案」，再决定是否放宽。

**模式 B：两级决策（Deterministic first, LLM second）**

```
唯一候选 / 支配比明显 → 机械直选（不花模型）
多候选 / 冲突       → jev(pick)（LLM）
证据不足            → jev 弃权 → 机械回退 → 仍不足则 escalate
```

**模式 C：有界闭环（Loop with cardinality branch）**

```
zero  → relax / pivot / fallback plan
one   → shape check → answer
few   → shape check → pick or direct
many  → tighten（补锚点）→ pick
```

**模式 D：兜底闭环（Escalate with predicate）**

坏 predicate：`fallback: agent(judge: "看看怎么办")`
好 predicate：`confidence < 0.6 OR no_plan OR waves_exhausted OR candidate_count > 12`

**模式 E：证据随行（Evidence travels with the decision）**

- jev(pick) 的候选必须带**可消歧的元数据**：所属告警、角色（Impacted/Related）、时间、实体类型、文件名/命令行特征；
- 但元数据要**结构化**，不要把整段原始 JSON 塞进对话（见 6.3 内容安全）。

### 2.9 DSL 反模式清单

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| 把整表/整段 JSON 作为候选 | 噪声稀释判断；触发内容过滤 | 去重、收窄到 ≤8、结构化 meta |
| 单候选加「语义闸门」 | 错在证据行/目标列，不在缺校验 | 先修计划层；闸门实测 −71pp |
| 候选越多越好 | 覆盖率↑但精度↓（122→157 覆盖，净 −1） | 先保证候选含 GT，再控制 ≤8 |
| 用题面点名保留噪声 | 「题面提到 PowerShell」≠「答案是 powershell.exe」 | 噪声只降权，不删除也不放回 |
| 用 test GT 调规则 | 过拟合，train 不涨 | 规则只看 schema/语义；test 只做最终验收 |
| DSL 只写文档不接执行 | 假实验 | P5 门禁：改参数必须改行为 |
| 答案按位置索引且频繁改计划 | 答案错位 | 计划追加到末尾 / 按值迁移 |

### 2.10 完整示例（跨领域最小骨架）

下面这个例子保留了 AgentRun 最初的形状：批量分类 → 确定性排序 → 有界检索 → 核心判定 → 升级 → 归档。它可以作为任何领域的起点。

```jsonc
chain {
  // 1. 批量分类：快速筛选出哪些输入项可能触发规则或风险（jev）
  map(over: "cards") {
    jev(classify: "Could this item trigger a high-severity stop under current policy?")
  },

  // 2. 确定性排序与过滤：高风险前置，过滤无关干扰项（code）
  code(logic: "sort_by_risk_and_prune_irrelevant"),

  // 3. 有边界的循环检索：限定轮次内并发获取必要证据（loop + research + verify）
  loop(until: "nothing_left_can_change_verdict", max_waves: 3) {
    map(over: "active_targets") {
      agent(research: "Fetch official records and digital footprint for the target"),
      jev(verify: "Check if evidence fully supports extracted claims")
    }
  },

  // 4. 核心判定与异常升级（escalate）
  escalate(
    predicate: "confidence_below_threshold",
    fallback: agent(judge: "Perform deep manual-grade reasoning on ambiguous evidence")
  ),

  // 5. 结果归档与报告生成
  code(logic: "compile_final_audit_record"),
  agent(report: "Render compliance deliverable")
}
```

> 注意：这个骨架对「边界」的约束不够强（`map` 没有并发上限、`loop` 的 until 不可机械判定）。
> 真正落地时必须补齐：并发上限、单步超时、`max_waves`、escalate predicate 的可判定性、trace 落盘。
> 参考第 2.4 节与第 6 章。

## P2　评测基座：没有可信的尺子，就没有爬山

### P2.1 目的

建立一个**冻结、确定、双口径、可逐题归因**的评测系统。

### P2.2 评测集设计

| 集合 | 规模 | 用途 | 规则 |
|---|---|---|---|
| **dev** | 100–300 | 日常迭代、快速反馈 | 可看错题、可诊断 |
| **test** | 100–500 | 最终验收 | 不参与调参；只在版本定稿后跑 |
| **train/generalization** | 50–200 | 泛化闸门 | 与 test 同分布但不同样本；不得用于调参 |

**冻结要求：**

- 固定 `seed`（本项目 `--seed 42`）；
- 固定样本清单（写进文件，不依赖运行时抽样）；
- 固定匹配规则（写进代码，版本化）；
- 固定 prompt 与工具版本；
- 每次评测输出带 `run_id`、时间戳、DSL 版本、答案库版本、代码 git hash。

### P2.3 匹配规则（必须显式定义）

本项目的规则（`executor.py`）：

```python
def norm(s):
    return re.sub(r'\s+', ' ', (s or '').lower()).strip()

def match(pick, gt):
    p, g = norm(pick), norm(gt)
    return p == g or (p and p in g) or (g and g in p)
```

**注意：**

- 双向包含适合「单实体抽取」，不适合数值/列表；
- 数值要用容差（如相对误差 ≤0.5% 或绝对误差 ≤1 单位）；
- 列表要定义集合匹配 / 顺序敏感；
- BI 场景推荐**执行结果比对**（canonicalize 后逐行比对），而不是比对 SQL 文本。

### P2.4 双口径输出

每次运行必须同时输出：

```json
{
  "run_id": "20261021T101500_v2.30_jev224",
  "dsl": "dsl_versions/v2.30.dsl.txt",
  "jev_ans": "jev/ans/v224.json",
  "seed": 42,
  "n": 522,
  "mechanism": {"correct": 283, "acc": 0.542},
  "with_answers": {"correct": 349, "acc": 0.669},
  "by_type": {"file": {"n": 124, "correct": 63}, "...": {}},
  "by_why": {"no_plan": 11, "waves_exhausted": 25, "shape_empty": 16, "many_abstain": 22},
  "flips": {"vs": "v2.27", "good_to_bad": [], "bad_to_good": []},
  "cost": {"sql_calls": 1234, "model_calls": 401, "latency_p50_s": 3.2, "latency_p95_s": 18.0}
}
```

### P2.5 确定性与噪声

- **同一配置跑两次**，差异应 ≤1 题；超过则先查：超时、并发、随机抽样、字典序、浮点。
- 本项目教训：`limit_s=45` 在高负载下偶发 timeout，同配置两次跑个别题「错→超时」；改为 90–120s 后稳定。
- 小样本噪声：50 题口径下 **1 题 ≈ 2pp**。train 50 的 +2pp 不能当显著提升；应使用「非退化」约束而非「+3pp」。

### P2.6 门禁

- [ ] 评测可一键复现；
- [ ] 两次运行差异 ≤1 题；
- [ ] 双口径都有数字；
- [ ] 分型 / why / flips 都能输出；
- [ ] 评测结果落盘且带版本元数据。

## P3　轨迹采集：让 agent 先跑一遍，别急着写规则

### P3.1 目的

拿到「人类专家/前沿 agent 实际怎么做」的完整证据链，作为蒸馏原料。

### P3.2 采样策略

| 维度 | 要求 |
|---|---|
| 数量 | ≥30 条成功轨迹；最好 50–100 |
| 分层 | 按答案类型、难度、数据源分层 |
| 成功定义 | 最终答案正确 + 过程可解释 |
| 失败样本 | 也保留 10–20 条，用于设计 escalate |
| 记录粒度 | 每次工具调用、每次模型输入/输出摘要、证据行 |

### P3.3 Trace schema（建议直接采用）

```jsonc
{
  "trace_id": "task_001",
  "task": {
    "input": "原始题面/问题",
    "context": "附加上下文（工单、告警、表结构）",
    "gold": "仅评测侧可见，trace 采集时可留空"
  },
  "steps": [
    {
      "i": 0,
      "type": "tool|reason|decision",
      "tool": "sql|http|search|code",
      "input": "SHOW TABLES",
      "output_summary": "33 tables",
      "evidence_rows": [["AlertEvidence","FileName","mimikatz.exe",153]],
      "tokens": {"in": 1200, "out": 300},
      "latency_ms": 800
    }
  ],
  "final_answer": "...",
  "correct": true,
  "cost": {"model_calls": 10, "tool_calls": 8, "tokens": 24000},
  "notes": "人工标注：哪几步是探索、哪几步是生产"
}
```

### P3.4 轨迹分析的五个问题

对每条轨迹，标注：

1. **哪些步骤是纯探索？**（`SHOW TABLES` / `DESCRIBE` / 分布统计）→ 可剪枝；
2. **哪些步骤是生产？**（参数化查询、JOIN、交叉验证）→ 沉淀为计划；
3. **哪些步骤是语义判断？**（「哪个 sender 才是答案」）→ jev；
4. **哪些步骤是校验？**（UPN 交叉验证、时间对齐）→ verify / escalate predicate；
5. **哪些步骤是报告？**→ Report agent。

### P3.5 门禁

- [ ] ≥30 条轨迹落盘；
- [ ] 每条有「探索/生产/判断/校验/报告」标注；
- [ ] 统计出探索步骤占比（本项目单题 3/8 = 37.5%）；
- [ ] 识别出前 5 类失败模式。

## P4　蒸馏：从轨迹到 DSL

### P4.1 目的

把「一条轨迹」抽象成「一个可参数化模板」，并证明它能覆盖多数样本。

### P4.2 四步蒸馏法

**Step 1：输入泛化（槽位化）**

从题面抽出稳定槽位：

| 槽位类型 | 例子 | 抽取方式 |
|---|---|---|
| 时间 | 「2026-08-04」「last quarter」「08:41」 | 正则 + 日期解析 |
| 实体 ID | IP、SID、GUID、PID、订单号、客户号 | 正则 + 校验 |
| 名称 | 告警标题、产品名、区域名 | 引号串 + 词典 |
| 动作 | 「removed」「删除」「复购」 | 关键词映射 |
| 度量 | 「revenue」「复购率」「GMV」 | 语义层词典 |

> 原则：**能从输入确定性抽出的，绝不交给模型**。

**Step 2：剪枝与直连**

- 删除所有探索动作（表清单、字段描述、分布 profiling）；
- 把表名、关联键、过滤条件在编译期固定；
- 用 2–4 条参数化查询直取候选集。

**Step 3：jev 判定**

- `sift`：行级过滤（外链/时间窗/类型）；
- `pick`：候选选择（≤8 个）；
- `verify`：单位/粒度/时间窗/交叉验证；
- 每个 jev 只做一件事。

**Step 4：熔断升级**

定义 3–5 个 predicate：

```
无候选 / 候选过多 / 交叉验证失败 / 置信度低 / 预算超限
```

任一触发 → `escalate` 到 judge agent（只读、步数预算、输出结构化）。

### P4.3 蒸馏产物

```
dsl_versions/v0.1.dsl.txt     # 模板骨架
data/semantic_layer.json      # 领域词典/先验（表→列、类型→列、指标定义）
data/priors.json              # 统计先验（只用于排序）
04_distill.md                 # 蒸馏记录：每条轨迹 → 模板的映射
```

### P4.4 覆盖度验证（P4 的核心门禁）

对 dev 集逐题编译，统计：

| 指标 | 要求 |
|---|---|
| 可编译率（能生成 ≥1 条计划） | ≥70% |
| 候选含答案率（gold ∈ candidates） | ≥80% |
| 唯一候选直选正确率 | ≥90% |
| 需要 escalate 的比例 | ≤30% |

> 本项目上界数据：492/522 可编译（94.3%）；唯一候选 113/115（98.3%）；多候选 GT∈候选 217/245（88.6%）；需兜底 162（31%）。

### P4.5 门禁

- [ ] v0.1 DSL 可执行（不是伪代码）；
- [ ] dev 集可编译率 ≥70%；
- [ ] 候选含答案率 ≥80%；
- [ ] 每个 jev 都有明确的输入/输出契约；
- [ ] 每个 escalate 都有可机械判定的 predicate。

## P5　Runner：DSL 必须真驱动执行

### P5.1 目的

把 DSL 变成唯一事实来源：**改 DSL 文件 = 改行为**。

### P5.2 架构

```
dsl_versions/vX.Y.dsl.txt
        │
        ▼
   dsl_parse.py  ──►  { chain: [nodes], params: {...} }
        │
        ▼
   runner.py
        ├── 节点分派：code → n_<logic> ；jev(kind) → j_<kind> ；loop → n_loop ；escalate → n_escalate
        ├── params 注入（DSL > CLI > 默认值；禁止 env）
        ├── trace 记录（每节点输入/输出/耗时）
        └── 评测输出（mechanism / with_answers / by_type / why / flips）
```

### P5.3 必备能力

| 能力 | 要求 |
|---|---|
| `--dsl <file>` | 必须；不给则用内置默认链（并打印警告） |
| `--tasks-file` / `--sample` / `--seed` | 固定评测 |
| `--tag` | rid 命名空间（test/train 同名 task_id 必须隔离） |
| `--jev-req <jsonl>` | pass A：无答案时写请求，并回退机械 |
| `--jev-in <json>` | pass B：注入 `{rid: index}` |
| `--eval-out <json>` | 落盘评测结果 |
| `--limit-s` | 单题超时（建议 90–120s） |
| `--trace-out` | 逐题 trace（含 SQL、候选、决策、why） |

### P5.4 rid 设计（答案库的稳定性基础）

```
rid = f"{tag}:{task_id}#{plan_index}"     # 例如 test:incident_39_64#0
rid = f"{tag}:{task_id}#bare"             # 裸查询兜底
rid = f"{tag}:{task_id}#classify"         # 分类请求
```

要求：

- 同一 rid 在 pass A / pass B 内容必须一致（确定性）；
- 改计划列表会改变 `plan_index` → 旧答案失效；
- **优先把新计划追加到末尾**，保持已有 index 稳定（本项目 v2.15 用此法把答案复用率做到 348/358）。

### P5.5 trace schema（运行时）

```jsonl
{"task_id":"...","plan_index":0,"anchors":{...},"asked_type":"file","family":"alert_attribute",
 "target":["AlertEvidence","FileName"],"sql":"SELECT ...","rows":12,
 "cands":[["mimikatz.exe",153],["psexesvc.exe",76]],
 "decision":{"node":"jev(pick)","rid":"test:...#0","answer":0,"conf":0.85,"status":"ans|none"},
 "why":"many_after_tighten","escalated":false,"latency_ms":120,"sql_calls":2}
```

### P5.6 门禁（非常重要）

- [ ] 修改 DSL 的某个 params 值，行为/分数必须变化；
- [ ] 删除 loop 内某节点，对应步骤必须消失；
- [ ] 任意一次运行可离线 replay（不重新调模型）；
- [ ] runner 代码中没有任何读取 gold 的路径（静态扫描 + 运行时断言）；
- [ ] `--tag` 生效，test/train 答案不串。

> **本项目教训**：runner 曾完全不读 DSL，版本文件只是文档，导致多轮「改了 DSL 分数不变」的假实验。P5 门禁就是防止这个。

## P6　答案生产：jev 的 LLM 作答协议

### P6.1 两种模式

| 模式 | 说明 | 适用 |
|---|---|---|
| **机械 jev** | 规则/支配比/形状匹配 | 基线、replay、LLM 未答时回退 |
| **LLM jev** | agent 或小模型对受限请求作答 | 提升上限；本项目净 +41 正确 |

### P6.2 两遍协议（pass A / pass B）

```
Pass A（收集）
  runner --jev-req req.jsonl --jev-in /dev/null
    → 每个需要决策的 jev 写一行请求；同时用机械规则作答（保证不丢分）
    → 产出 req.jsonl + 机械基线分数

人工/LLM 作答（离线）
  req.jsonl → 去敏 → 分批阅读 → 写答案 {rid: index 或 -1}

Pass B（注入）
  runner --jev-req req_b.jsonl --jev-in ans.json
    → 有答案用答案；无答案/ -1 回退机械
    → 产出含答案分数 + 新的请求（可选）
```

### P6.3 请求 schema

```jsonc
{
  "rid": "test:incident_39_64#0",
  "task_id": "incident_39_64",
  "node": "pick",
  "asked_type": "file",
  "family": "alert_attribute",
  "question": "原始题面",
  "context": "附加上下文",
  "anchors": {"alert": ["..."], "host": ["..."], "ts": ["..."]},
  "target": ["AlertEvidence", "FileName"],
  "cands": [["mimikatz.exe", 153], ["psexesvc.exe", 76]],
  "meta": [
    {"alert": "A1", "role": "Impacted", "time": "08:41:20", "etype": "Process", "file": "V1"}
  ],
  "choose": "cands 下标；-1 = 弃权交回机械"
}
```

### P6.4 作答原则（写进给 LLM 的 system prompt）

1. **只根据题面、锚点、候选、结构化 meta 判断**；不得读取 gold；
2. **证据不足就弃权（-1）**，不要猜；
3. 优先使用「可复核」的信号：
   - 候选是否属于题面点名的告警；
   - 时间是否与题面 HH:MM 对齐；
   - 实体类型是否与所问列匹配；
   - 角色是否 Impacted；
   - 值是否与另一张表的同名实体互证；
4. 不要用「高频/常见」作为理由（那是机械先验，不是语义）；
5. 输出只允许 `{"rid": int}`。

### P6.5 防泄漏

**物理隔离**（不能只靠提示词）：

```bash
mkdir -p _gt_isolation
mv eval/tasks_test.json _gt_isolation/
# 作答完成后再迁回
```

**泄漏事后检测**（必做）：

对每批答案，计算「gold ∈ cands」子集上的答对率：

| 答对率 | 自认错误数 | 判定 |
|---|---|---|
| ~100% | 0–1 | **疑似泄漏**，作废重做 |
| 85–95% | 有若干 | 合法（语义歧义会犯错） |
| 明显低于机械基线 | — | 可能理解错误，抽检 |

> 本项目：p2 = 29 条中 26 对（90%，3 错）→ 合法；p3 = 35/35（100%）→ 判为泄漏，作废。

### P6.6 内容安全与去敏（P6 的硬门槛）

**事故复盘**：jev 请求里包含安全事件原文（mimikatz 命令行、NTDS 导出、Defender 篡改），直接贴进对话触发模型侧内容过滤，会话中断。统计：401 条请求中 152/199 条带高风险词，43 条含 ≥3 个；最典型一条 65KB 原始 JSON。

**协议：原文不进对话。**

```
原始请求（本地）
   │  safe_view.py build
   ▼
去敏视图（可进对话）
   ├─ 告警标题 → A1/A2 + 安全类别（FRAUD/SIGNIN/TAMPER/...）
   ├─ 实体值   → V1/V2（题面、候选、meta 共用同一张表，指代关系不变）
   ├─ 敏感词   → 中性词（mimikatz→tool-x, powershell→shell, credential→secret）
   ├─ meta 文本→ 结构化字段 alert/cat/role/time/etype/asked_match
   └─ 候选值   → 补充 shape（ip/email/guid/sid/exe/dll/script/archive/doc/num）与 kind
   │  safe_view.py scan  → 必须 risk hits: 0
   ▼
按批阅读（每批 ≤20 条）
   │  写答案 {rid: index}
   ▼
safe_view.py merge → 新答案库
```

**保真性要求：**

- 候选数、顺序、候选↔meta 对应、告警归属、角色、时间全部保留；
- 答案本来是下标，值换成占位符不影响可答性；
- 标题**不做局部替换**（截断会产生 "A1related user" 这类碎片）。

**补充工具 `safe_score.py`**：如果去敏视图丢失了「字面重合」信息，可在本地用原始请求算数值特征（标题重合度、题面点名、锚点命中、类型匹配、角色、计数、时间差），只把**数值 reason code** 交给模型裁决。原则：**原始数据只进本地脚本，不进对话。**

### P6.7 答案库治理

| 规则 | 说明 |
|---|---|
| 版本化 | `jev/ans/v1.json`, `v2.json` …；每次实验用明确版本 |
| 不可变 | 已发布的答案库不原地修改；新版本另存 |
| 可追溯 | 每条答案记录 `rid / answer / source(batch) / date / reviewer` |
| 弃权显式 | `-1` 表示弃权，不是「没答」 |
| 迁移 | 改候选集时按**值**迁移，不按位置（见 5.4） |
| 审计 | 每批做泄漏审计 + 抽检 10% |

### P6.8 门禁

- [ ] 请求覆盖率 ≥90%（需要决策的节点都有请求）；
- [ ] 去敏扫描 `risk hits: 0`；
- [ ] 泄漏审计通过；
- [ ] 弃权率可解释（本项目弃权 ≈ 20–30%，且机械回退常更准）；
- [ ] pass B 分数 ≥ 机械基线（否则答案有害）。

## P7　爬山：诊断 → 假设 → 版本 → 测量 → 判定

### P7.1 目的

用最小实验成本，稳定提升机制侧分数，同时保证泛化。

### P7.2 每轮七步（不可跳）

```
1. 诊断：用漏斗把错题分层（见 P7.3），选出最大且可解的一层
2. 假设：写清「改什么、为什么、预期 +N 题、怎么证伪」
3. 单变量：一轮只改一个机制（或明确隔离的 A/B）
4. 版本文件：先落 dsl_versions/vX.Y.dsl.txt，再跑
5. 测量：test 522（机制侧）→ 若达标再跑 train 50
6. 判定：看净分 + 翻转（好→坏 / 坏→好）+ 分型变化
7. 记录：ledger 一行；不采纳也要写「为什么」
```

### P7.3 漏斗分层（诊断的核心工具）

对每条错题，按「gold 在哪一步丢失」分类：

| 层 | 定义 | 可动性 |
|---|---|---|
| **NO_PLAN** | 所有计划 SQL 返回 0 行 | 锚点/绑定过死 |
| **BIND** | 列选对、整列含 gold，但 WHERE 没命中 | 绑定/时间窗过窄 |
| **COL_NEVER** | 没有任何计划指向含 gold 的列 | 需要新计划/映射表 |
| **SHAPE** | SQL 原始行有 gold，被 shape/noise 删掉 | 形状/噪声规则 |
| **CAPPED** | gold 排名 > cands_cap | 候选上限 |
| **PICK** | gold 已在候选里，选错 | jev/答案层 |

本项目 v2.27 的 181 错分层：PICK 68 / BIND 45 / COL_NEVER 34 / SHAPE 21 / NO_PLAN 11 / CAPPED 2。

**诊断脚本骨架：**

```python
# diag.py —— 只读 gold 做离线诊断，不参与求解
for task in test_set:
    trace = load_trace(task)
    gold = task["gold"]
    layer = classify_loss(trace, gold)
    # NO_PLAN: all sql rows == 0
    # COL_NEVER: no plan target column contains gold in full column
    # BIND: full column contains gold, but bound query rows don't
    # SHAPE: bound rows contain gold, but shape_filter removed it
    # CAPPED: gold rank > cands_cap
    # PICK: gold in cands[:cap] but answer != gold
    record(task, layer)
```

### P7.4 假设模板

```markdown
## Round N / 组 M：<机制名>

**层级**：BIND / 45 题
**诊断证据**：<SQL/统计/样例 rid>
**假设**：把 <X> 改成 <Y>，能让这 45 题里的 <K> 题走到正确候选；预期 test 机制 +K 题（+K/522 pp）
**证伪条件**：若翻转中「好→坏」≥「坏→好」，或分型 <某类> 下降超过预期，则回滚
**影响面**：是否改变计划顺序/候选集？→ 是则先做答案迁移
**单变量**：本轮只改这个；其他参数保持 vX.Y
```

### P7.5 接受 / 回滚规则

| 规则 | 说明 |
|---|---|
| **主判据** | 机制侧 test ≥ +3pp（522 口径约 +16 题） |
| **泛化闸门** | train 50 不退化（≥ 基线 −1 题）；50 样本 1 题 = 2pp，不要求 +3pp |
| **翻转分析** | 好→坏必须显著少于坏→好；若接近，视为噪声 |
| **分型检查** | 目标类型必须涨；不能靠牺牲其他类型换净分 |
| **答案迁移** | 若改了候选集/计划顺序，必须先迁移答案库，否则分数不可比 |
| **回滚** | 不达标要**真正回滚代码/参数**，不能只标记「不采纳」却留在默认路径 |
| **例外** | 机制级、train 同向、0 回退的改动，可按「裁定 A」保留并记录理由 |

> 本项目裁定 A：G2 在 test +3.1pp、train 持平，按字面应弃，但机制级、非 GT 蒸馏 → 保留。
> 本项目裁定 B：所有 jev 统一用 LLM 模拟，机械规则只作回退。

### P7.6 负结果也是资产

每轮必须记录：

```markdown
| 版本 | 改动 | test 机制 | train | 翻转 | 判定 | 原因 |
|---|---|---|---|---|---|---|
| v2.31 | thin_relax + relax_empty_nobind | 346 (−3) | — | 6 好→坏 / 3 坏→好 | 不采纳 | 放宽后噪声顶掉正确答案 |
```

**负结果登记表的价值**：本项目有 6+ 次「放宽绑定/放回噪声」的负结果，如果不登记，后来者会反复重试。

### P7.7 实验节奏

- 每轮 1–3 个版本，最多 3 轮后**强制重新诊断**（避免在错误方向上连续微调）；
- 每轮结束更新 `06_ledger.md` + `dsl_versions/README.md` + `state.md`；
- 每次只跑必要的集合：dev 快速筛 → test 确认 → train 泛化；
- 长跑用非阻塞 + 轮询，中间结果落盘。

### P7.8 门禁

- [ ] 至少 3 轮完整记录；
- [ ] 每轮有诊断证据、假设、翻转分析；
- [ ] 不采纳的改动已真正回滚；
- [ ] 版本文件可执行且与默认路径一致；
- [ ] train 未被用于调参（只做闸门）。

## P8　收割与天花板：知道什么时候停

### P8.1 两种收益来源

| 来源 | 特征 | 风险 |
|---|---|---|
| **机制侧** | 改计划/绑定/形状/分类/映射 | 低；可泛化 |
| **答案侧** | 只改 jev 答案库 | 高；易过拟合，需审计 |

### P8.2 什么时候可以「收割答案」

满足全部条件才做：

1. gold 已在候选集（PICK 层）；
2. 有**可复核的决定性上下文**（不是 meta 文本猜测）：
   - 候选属于题面点名的告警；
   - 时间与题面 HH:MM 对齐（查 `AlertId × Timestamp`）；
   - 与另一张表的同名实体互证；
   - 角色/类型匹配；
3. 逐条改判，不批量；
4. 改判后必须跑 test + train，记录翻转；
5. 若「好→坏」出现，立即停止该方向。

> 本项目：Round 19 逐条精读 72 条「候选含 GT 却错/弃权」，只对 28 条有决定性上下文的改判 → 302→323（+21，单轮最大收益）；Round 20 再用「逐告警时间对齐」改 5 条 → 327。

### P8.3 什么时候必须停

| 信号 | 含义 | 动作 |
|---|---|---|
| 连续 4 次答案侧负结果 | 弃权/补答方向关闭 | 停止批量补答 |
| 连续 4 次放宽类负结果 | 局部最优确认 | 转向工程/文档收尾 |
| PICK 层无可验证新信号 | 上限受证据限制 | 只做 DB 可复核覆盖 |
| 机制侧改动 0 翻转 | 改动无效/死变量 | 先验证变量是否真的被使用 |
| 分型下降但净分上涨 | 拆东墙补西墙 | 不采纳 |

> 本项目最终结论：v2.30 = 349/522（66.9%）、train 23/50 是局部最优；剩余可动的只有「DB 可复核的 PICK 覆盖」，放宽绑定/放回噪声全部负结果。

### P8.4 天花板估算

用分层上限做加法：

```
当前正确 349
  + PICK 层可复核覆盖（假设 30% 可解）      ≈ +20
  + COL_NEVER 中的映射/分类修正（20 条）    ≈ +10
  + BIND 的薄行回退（若有可验证信号）        ≈ +5
  = 理论上限 ≈ 384（73.6%）
```

如果目标 >70%，需要至少 PICK + COL_NEVER 两块都兑现；只做一块不够。

### P8.5 门禁

- [ ] 有完整残量分层；
- [ ] 有天花板估算与依据；
- [ ] 已明确「关闭的方向」及关闭理由；
- [ ] 答案库有版本与审计记录；
- [ ] 下一阶段（生产化）的输入已齐。

# 第五部分　实验纪律

## 5. 五条纪律

### 5.1 先诊断，再动手

- 任何机制改动前，必须先用漏斗证明「目标层有多大、为什么错」；
- 诊断结论必须用**第二种独立口径**复核（本项目曾出现「shape 误杀 37 vs 0」的矛盾，动手前必须第三方复核）；
- 不要凭直觉改（本项目 v2.18 的 `device_id_guard`、noise 降权都是「按错误归因改代码」）。

### 5.2 单变量与可证伪

- 一轮只改一个机制；多个改动必须能独立 A/B；
- 假设必须写「预期 +N 题」和「证伪条件」；
- 结果必须看**翻转**，不只看净分；
- 若改动「0 翻转」，先验证变量是否真的被使用（本项目 `_jev_extra` 死变量导致误判 v2.22 无效）。

### 5.3 口径与显著性

- 机制侧是主判据；含答案只作参考；
- 522 题：1 题 = 0.19pp；+3pp ≈ +16 题；
- 50 题：1 题 = 2pp；用「非退化」而非「+3pp」；
- 同配置两次跑差异 >1 题 → 先修确定性，再谈提升。

### 5.4 答案库失效与迁移

**什么时候失效：**

- 计划顺序变化 → `plan_index` 变；
- 候选集/候选顺序变化 → 下标含义变；
- 分类变化 → 请求集合变；
- rid 命名空间变化。

**迁移策略（按优先级）：**

1. **保持顺序**：新计划追加到末尾，老 index 不动（v2.15 做法，复用率 348/358）；
2. **按值迁移**：记录每个 rid 的 `cand_value`，新候选集里找同值 → 新 index；
3. **按语义迁移**：用 `(task, plan_target, cand_value)` 三元组匹配；
4. **重新作答**：以上都不可行时，pass A 重收 + 重答（成本最高）。

**反例**：v2.28 改噪声策略导致候选列表变化，答案按位置索引整体错位，分数 341→314（−27），而机制本身可能是对的。

### 5.5 负结果登记表（防重蹈）

| 方向 | 尝试次数 | 结果 | 结论 |
|---|---|---|---|
| 放宽绑定（thin_relax / relax_empty_nobind） | 2 | −3 / 更差 | 噪声顶掉正确答案 |
| 放回噪声（noise_keep_aeid / rank / named / ext） | 4 | −11 / −4 / −5 / −1 | 题面点名 ≠ 答案是它 |
| 扩候选（WIDEN*） | 3 | 194 / 193 / 174 | 覆盖率↑但精度↓ |
| 单候选语义闸门 | 2 | 122 (−71pp) / 176 (−17pp) | 错在证据行，不在缺校验 |
| 批量补答弃权 | 4 | 338 (−2) 等 | 弃权后机械更准 |
| 遥测二跳（含按问句选列） | 4 | 226 / 229 / 225 / 244，均未超 v2.17 的 247 | 方向关闭 |
| 行级上下文喂 jev | 1 | 250 (−3) | 弱证据覆盖掉分 |

### 5.6 反泄漏审计清单

- [ ] GT 物理隔离，求解路径不可达；
- [ ] runner 静态扫描无 `gold` / `gt` 读取；
- [ ] 子 agent 的 prompt 不含 GT 路径；
- [ ] 答案批次的「gold∈cands 答对率」不是 100%；
- [ ] 诊断脚本明确标注「只用于离线归因」；
- [ ] 训练/测试/泛化集不重叠（同名 task_id 用 tag 隔离）。

# 第六部分　工程 Runbook

## 6. 踩过的坑与标准动作

### 6.1 持久化与会话中断

| 问题 | 标准动作 |
|---|---|
| 会话中断，结果只存在内存 | 每个阶段结束落盘；长任务中间结果每 N 条落盘 |
| `/tmp` 被清空 | 禁用 `/tmp` 存关键资产；启动时检查 |
| 子 agent 结果丢失 | 子任务输出直接写文件，不只返回文本 |
| 环境重置依赖丢失 | 启动脚本检查依赖；锁定版本 |

### 6.2 长任务与非阻塞

```bash
# 好：后台 + 轮询 + 落盘
nohup python3 runner.py ... > runs/v2.30.log 2>&1 &
# 轮询
tail -f runs/v2.30.log
```

- 单题超时 90–120s；
- 批任务加 `--resume`（跳过已完成 task_id）；
- 失败题单独重跑，不整批重来。

### 6.3 内容安全

**触发条件**：请求体包含恶意工具名、凭据、攻击命令、PII、医疗/金融敏感信息。

**标准动作：**

1. 原始数据只在本地脚本处理；
2. 进对话前必须去敏；
3. `scan` 必须 0 命中；
4. 分批 ≤20 条；
5. 不把整段原始 JSON 当候选；
6. 用结构化字段替代自由文本 meta。

### 6.4 性能与超时

| 现象 | 原因 | 处理 |
|---|---|---|
| 同配置两次结果不同 | 超时/并发/浮点 | 提高 timeout；固定并发；排序稳定 |
| SQL 越来越慢 | 计划膨胀/全表扫描 | `plan_cap`；索引；分区过滤 |
| 内存涨 | 缓存 trace | 流式写盘；限制缓存 |
| 模型调用超预算 | 候选太多/触发面太广 | `cands_cap`；限制 jev 触发条件 |

### 6.5 确定性

- 排序必须有稳定 tie-breaker（值字典序 / 行号）；
- 集合遍历用 `sorted()`；
- 随机只用于抽样，且 seed 固定；
- 时间用固定时区；
- 浮点比较用容差；
- 并发写文件用独立文件 + 合并。

### 6.6 调试与三方复核

当两个口径结论矛盾时：

1. 写第三个独立脚本，用不同实现重算；
2. 抽 5 条样本手工执行 SQL/流程；
3. 对比中间产物（候选集、shape 结果、答案）；
4. 只有三方一致才动手改代码。

> 本项目教训：Round 22 的「shape 误杀 37」被第三口径推翻为「noise 硬删 57」，如果直接按 37 改 shape，会改错地方。

### 6.7 常见故障速查

| 故障 | 排查 |
|---|---|
| `ModuleNotFoundError` | 依赖未装；启动脚本 `pip install -r requirements.txt` |
| 评测 0 分 | 检查 tasks 文件路径、GT 字段名、匹配规则 |
| 答案不生效 | rid 不匹配（tag/plan_index）；答案库版本错 |
| 改了 DSL 没变化 | runner 没读 DSL；参数名拼错；默认值覆盖 |
| 分数突然大跌 | 候选集变了但答案没迁移；超时；数据快照变了 |
| 请求里出现 GT | 隔离失效；检查 `_gt_isolation` 和代码路径 |

# 第七部分　领域迁移：以 BI 分析为例

> 本节把 P0–P9 在一个**完全不同的领域**完整走一遍。目标是证明：只要把「锚点 / 计划 / 候选 / jev / escalate / 评测」映射对，AgentRun 可以跨领域复用。
> 示例数仓为虚构，替换为你的真实表名即可。

## 7.0 BI 任务画像

**输入**：业务人员自然语言问题，例如：

- 「上个季度华东区新客的复购率是多少？」
- 「对比今年和去年双 11 的 GMV，按品类拆。」
- 「找出过去 7 天退款率超过 5% 的门店。」

**输出**：一个数值 / 一张表 / 一段带口径说明的结论。

**现状痛点**：

- 每次都要 agent 探索 schema、找表、猜口径；
- 同一个问题不同人得到不同数字（口径不一致）；
- 全表扫描成本高、延迟大；
- 无法审计「为什么是这个数」。

**迁移目标**：

- 80% 常规问题走固定流程（语义层 + 计划 + jev）；

## 7.5 P4：DSL 设计（BI 版）

```text
// ============================================================================
// BI DSL v0.1 — 指标取数模板
// 输入：自然语言问题 + 语义层 + 只读数仓
// 结构：锚点 → 意图分类 → 主题路由 → 计划 → 循环 → 兜底
// ============================================================================

params {
  "max_waves": 4,
  "cands_cap": 6,
  "conf_min": 0.6,
  "numeric_tol": 0.005,
  "max_scan_gb": 50,
  "query_timeout_s": 60,
  "default_timezone": "Asia/Shanghai",
  "require_partition_filter": true,
  "readonly": true
}

chain {
  // 0. 题面锚点：时间、区域、品类、门店、指标词、过滤词
  code(logic: "extract_anchors", out: "anchors"),

  // 1. 意图分类：标量 / 趋势 / 拆分 / 对比 / TopN / 比率 / 列表
  jev(classify: "What kind of analytical question is this?",
      enum: [scalar, trend, breakdown, compare, topn, ratio, list],
      pre_rules: "bi_intent_map",
      out: "intent, measure_hint"),

  // 2. 主题路由
  jev(route: "Which subject area should answer this?",
      branches: { sales, retention, marketing, ops, finance, unsure },
      out: "subject"),

  // 3. 计划：指标变体 × 维度 × 时间粒度 × 过滤
  code(logic: "build_plan", in: "intent, subject, anchors, semantic_layer",
       out: "ordered_queries"),

  // 4. 有界循环
  loop(until: "answered == true", max_waves: 4) {
    call(tool: "sql", query: "ordered_queries[wave]", out: "rows",
         guard: {readonly: true, partition_required: true,
                 max_scan_gb: 50, timeout_s: 60}),
    code(logic: "cardinality_branch", out: "zero | unique | few | many"),
    code(logic: "relax_or_pivot", when: "zero"),
    code(logic: "tighten", when: "many"),

    // 5. jev：口径/维度值选择
    jev(pick: "Which metric definition and dimension value match the question?",
        when: "few | many",
        in: "question, anchors, metric_dict, cands[:6]",
        out: "index | -1"),

    // 6. jev：粒度/单位/时间窗校验
    jev(verify: "Does the result answer the question at the right grain, unit, and time window?",
        in: "question, anchors, result_schema, sample_rows",
        out: "confidence"),

    code(logic: "format_answer")
  },

  // 7. 兜底：只读探索 + 明确 predicate
  escalate(predicate: "confidence < conf_min OR waves_exhausted OR scan_budget_exceeded OR metric_ambiguous",
           fallback: agent(judge: "Read-only warehouse exploration. 12 steps max. Return metric, SQL, result, and assumptions.")),

  // 8. 报告与审计
  agent(report: "Render answer with metric definition, SQL, filters, and caveats"),
  artifact(logic: "persist_trace",
           fields: [anchors, intent, subject, queries_tried, metric_variant,
                    confidence, scan_gb, fallback_used])
}
```

**BI 的 jev 设计要点：**

| jev | 问题 | 输入 | 输出 |
|---|---|---|---|
| classify | 这是标量/趋势/拆分/对比/TopN/比率？ | 题面 + 指标词典 | 枚举 |
| route | 属于销售/留存/营销/运营/财务？ | 题面 + 锚点 | 分支 |
| pick | 用哪个指标变体/维度值？ | 语义层候选 + 题面 | 下标/弃权 |
| verify | 粒度/单位/时间窗对吗？ | 结果 schema + 样本行 | 置信度 |

**BI 的 escalate predicate：**

```text
口径有多个 variant 且证据不足
指标在语义层不存在
多表结果冲突
扫描预算超限
结果为空且放宽后仍为空
置信度 < conf_min
```

## 7.6 P5：Runner（BI 版）要点

- **SQL guardrail**：只读、强制分区/时间过滤、`LIMIT`、扫描字节上限、超时；
- **SQL 生成**：从 `(metric, dimensions, filters, time)` 模板化生成，不让模型自由写 SQL；
- **结果规范化**：列名、行序、数值精度、NULL、时区；
- **trace**：记录 SQL、扫描字节、候选口径、选择理由；
- **回放**：缓存 SQL 结果（带数据快照版本），离线重放。

## 7.7 P6：答案生产（BI 版）

- 请求 = 「在 3 个复购率口径中选哪个」+ 题面 + 语义层摘要 + 候选定义；
- 答案 = 下标；弃权 = -1；
- 去敏：客户姓名/手机号/邮箱 → V-id；金额可保留但脱敏为区间（若敏感）；
- 审计：gold 口径在候选中时的答对率不应是 100%。

## 7.8 P7：爬山（BI 版可做的机制）

| 优先级 | 机制 | 预期 | 验证 |
|---|---|---|---|
| 1 | 指标同义词扩展 | 提高 classify 命中 | dev 编译率 |
| 2 | 时间粒度/财年映射 | 减少时间窗错误 | 分型 |
| 3 | 维度值字典（region/category 别名） | 减少 zero 计划 | NO_PLAN 层 |
| 4 | 比率分母/去重规则 | 修复 fan-out | 执行结果比对 |
| 5 | 口径冲突检测 | 提高 verify 准确 | escalate 率 |
| 6 | 结果空时放宽策略 | 提高覆盖率 | 但注意噪声（本项目负结果） |

**不要做**：放宽时间过滤到全表、把多口径结果都返回、让 LLM 自由写 SQL。

## 7.9 P8：天花板与停止

- PICK 层：口径选择错误；
- BIND 层：过滤条件过窄；
- COL_NEVER：指标未建模；
- SHAPE：单位/币种/时区不一致；
- CAPPED：候选口径太多。

当「放宽」连续负结果、PICK 无可验证信号时停止，转向语义层治理。

## 7.12 BI 常见坑

| 坑 | 症状 | 处理 |
|---|---|---|
| fan-out | JOIN 后金额翻倍 | 先聚合后 JOIN；或明确 grain |

## 8.3 关键事实（可直接引用）

1. **jev 交给 LLM 是真收益**：+49 正确 / −8 错误（净 +41），但「LLM 只加分」不成立。
2. **train 的「不变」可能是测法错**：答案按 task 注入时 train 天然不生效；单独产答案后 +16pp。
3. **rid 必须带命名空间**：test/train 17 个同名 task_id，共用答案库污染 4 个 pick。
4. **题面时间锚点与 DB 时间轴按 incident 偏移**：39:−7d、5:−14d、55:−2d、166:0；`ts` 绑定在很多 incident 上永远匹配不到行。
5. **C 组根因不是选错列**：GT 95/104 可按值定位；是绑定/时间窗把证据切得太窄。
6. **单候选语义闸门有害**：−71pp / −17pp。
7. **扩候选不赚**：覆盖率 122→157，但候选从 2–3 涨到 8，稀释判断，净 −1。
8. **超时是真实噪声**：`limit_s=45` 高负载偶发 timeout；建议 90–120s。
9. **PID 的答案在 `AlertEvidence.AdditionalFields`**：二次转义 JSON 含 `ProcessId/CommandLine/ImageFile.Name`；候选必须带进程身份。
10. **「打通 AlertId 强关联」不是最大增量**：aeid 已覆盖 396/522；真正缺口是「无计划 97」与「alert_ids 失败 74」。
11. **改候选集必迁答案库**：v2.28 −27 纯属位置索引错位。
12. **结论要落到「变量是否真的被使用」**：`_jev_extra` 死变量导致误判 v2.22 无效。
13. **两次测量矛盾必须第三方复核**：shape 误杀 37 vs 0，最终证实是 noise 硬删 57。
14. **原文不能直接进对话**：401 条请求中 152/199 含高风险词，触发内容过滤，会话中断。
15. **DSL 必须真驱动**：runner 曾完全不读 DSL，版本文件只是文档。

# 第九部分　给 Coding Agent 的执行契约

> 这一章是「自主完成迁移」的操作系统。Agent 每个会话都应按此执行。

## 9.1 会话启动流程（每次必做）

```
1. 读 state.md          → 当前阶段、下一步、阻塞项
2. 读 06_ledger.md 尾部 → 最近 3 轮实验与判定
3. 检查资产            → data / eval / dsl_versions / jev 是否齐全
4. 跑 smoke test       → 1 条样本，确认 runner 可执行
5. 跑确定性检查        → 同配置两次，差异 ≤1 题（或只跑 20 条快检）
6. 开始工作            → 只做 state.md 里的下一步；不要即兴开新方向
```

## 9.2 每轮工作循环

```
诊断（读 trace + 漏斗）
  → 写假设（预期 +N、证伪条件）
  → 落版本文件（先写注释：动机/改法/预期）
  → 跑 dev（快）
  → 跑 test（机制侧）
  → 若达标：跑 train（泛化闸门）
  → 判定：采纳 / 回滚
  → 更新 ledger + dsl README + state.md
  → 落盘 + 备份
```

## 9.3 绝对禁止

| 禁止 | 原因 |
|---|---|
| 把关键文件放 `/tmp` | 会被清空（本项目丢过 GT） |
| 在求解路径读 gold | 作弊，成绩无效 |
| 把原始敏感数据贴进对话 | 触发内容过滤，会话中断 |
| 批量补答弃权 | 4 次负结果 |
| 放宽绑定/放回噪声「试试看」 | 6 次负结果 |
| 不落版本文件就评测 | 结果不可复现 |
| 只标记不采纳但不回滚代码 | 默认路径被污染 |
| 用 train 调参 | 泛化闸门失效 |
| 改候选集不迁移答案 | 分数不可比（v2.28 −27） |
| 声称「无效」而不验证变量是否被使用 | 死变量误判 |

| 方向连续 4 次负结果 | 关闭方向，写进负结果登记表，转下一层 |
| 达到局部最优 | 转 P9 工程收尾，不再微调 |

## 9.5 交付标准（Definition of Done）

一个「端到端迁移完成」必须同时满足：

- [ ] **可执行**：`dsl_versions/` 下每个版本都能直接跑；
- [ ] **可复现**：同配置两次差异 ≤1 题；有固定 seed 与快照；
- [ ] **双口径**：机制侧 / 含答案都能输出；
- [ ] **可解释**：每题有 trace（计划、SQL、候选、决策、why）；
- [ ] **可回放**：不重新调模型即可复现答案；
- [ ] **可审计**：答案库有版本、来源、泄漏审计；
- [ ] **可兜底**：escalate predicate 明确，judge agent 有预算；
- [ ] **可运维**：成本/延迟/漂移监控；
- [ ] **可交接**：README + state + ledger + runbook + 负结果清单；
- [ ] **不降级**：机制侧不低于基线；jev 全失效时仍有兜底。

## 9.6 汇报格式（每次会话结束）

```markdown

- 阶段：
- 做了什么：
- 结果（数字 + 翻转）：
- 判定（采纳/回滚/中性）：
- 落盘位置：
- 下一步（≤3 条）：
- 阻塞/风险：
```

## 9.7 自主运行的边界

Agent 可以自主决定：

- 诊断方法、抽样策略、脚本实现；
- 在既定方向上做单变量实验；
- 在门禁内选择采纳/回滚；
- 补文档、补测试、补监控。

Agent 必须向人确认：

- 改变验收口径/目标；
- 引入新的外部依赖或写权限；
- 处理 PII/合规敏感数据；
- 删除历史资产；
- 连续 4 次负结果后是否转向。

# 附录 D　一页总结

```
目标：把高频、可验证的 agentic task 沉淀为 AgentRun 流程。
方法：P0 立项 → P1 资产 → P2 评测 → P3 轨迹 → P4 蒸馏 → P5 Runner
      → P6 答案 → P7 爬山 → P8 收割 → P9 生产。
铁律：锚点驱动、GT 隔离、先验只排序、jev 弃权回退、放宽需证明、改候选必迁答案。
验收：机制侧 test ≥ +3pp；train 不退化；翻转分析；可回放；可审计。
停止：连续 4 次负结果；PICK 无新信号；达到局部最优。
交付：版本文件 + 台账 + 答案库 + 评测 + runbook + 负结果清单。
```

> **最后一句话**：AgentRun 的收益不来自「更聪明的模型」，而来自「把不确定性收窄到少数可审计的判定点」。任何让候选变多、让绑定变松、让模型自由发挥的改动，都要先证明它不会让噪声顶掉正确答案。
